# 3.0.8 封包图标抓取完善 — 阶段1 + 阶段3 已完成

## 一、问题定位

现象：「封包里的图标基本没出来，导出数量明显偏少，但导出的文件本身是好的」
→ 不是解密算法坏，而是**封包内的文件名清单从来没被枚举过**。

证据：0.11.5 原代码对新引擎把 `themeFileMap / diyFileMap / themeData / _fileIndex / ThemeBoxUtil.shared`
全部用 `newEngine?nil:` 硬性跳过，只认 `themeFiles`（散装目录）和运行时已解密缓存。
主题盒子自己的完整名字表（`ThemeBoxUtil` 类方法那一组 `*FileList`）**一次都没被查询**。

## 二、样本分析结论（决定了修复路线）

对你给的 `themebox.dat`（10,917,408 字节，SHA256 `b5f3fa2b…61355`）做了完整二进制取证：

| 检验 | 结果 | 含义 |
|---|---|---|
| Shannon 熵 | **8.0000 bit/byte**（理论最大） | 全文件无冗余，纯密文 |
| 682,338 个 16 字节块 | **零重复** | 排除 ECB / 弱分组模式 |
| lag 1~4096 自相关 | 全部 ≈ 0.0039 随机基线 | 排除定密钥 XOR / 简单流密码 |
| 可打印率 | 0.371，所有 4096 窗口落在 0.346~0.394 | **没有任何明文区**：无明文头、无明文索引、无 manifest |
| `gzip` / `JPEG` 魔数 | 命中但解压/解码失败 | 随机巧合，不是误判为密文的明文 |
| 文件长度 | 10917408 = 682338×16 | 16 字节对齐，典型分组密码密文 |

**结论：密钥和文件名索引都不在 dat 里，而在主题盒子运行时。**
所以"离线直接解包 dat"这条路不成立——我撤回阶段2最初提的那个方向。
唯一可行路径是：**让主题盒子自己解密，我们按名字向它要字节**。

## 三、已完成的改动

### 阶段1：运行时 ivar 探查（`SaoqiangWCAssetsThemePack.m`）

1. 新增 `SQCollectNameStrings` / `SQCollectIvarNames`：运行时遍历
   `ThemeBoxAssets` / `ThemeBoxUtil` / `ThemeBoxCache` 实例的**对象型 ivar**，递归提取字符串候选名。
   不硬编码任何 ivar 名、偏移、版本号或 UUID —— 符合原项目「运行时验证、不按版本硬锁」的原则。
2. 新增 `SQPlausibleResourceName`：只保留形态像资源名的候选（图片扩展名或无扩展名、无空白、非绝对路径、不含 `..`），
   过滤主题描述、UUID、配色名、封包名等噪音。
3. 去掉新引擎的 getter 门控：`themeFileMap / diyFileMap / themeData / bubbleFiles / ThemeBoxUtil.shared`
   现在对所有引擎都用 ABI 校验后的 `SQGet` 探测（签名不符自动返回 nil，安全）。
4. **候选与权威清单分离**：ivar 候选取不到字节只计 `skipped`，不虚增 `missing/failed`。

### 阶段3：接入主题盒子自带的原生解密器（新增 `SaoqiangWCAssetsNative.{h,m}`）

从 `主题盒子3.0.8_roothide（隐根）.deb` 中取出的 `ThemeBox.dylib`（23,349,440 字节）里，
符号表暴露了它内嵌 Rust 静态库的 C ABI（764 个符号），反汇编确认了调用约定：

```c
int  theme_box_contains_file(const char *name);            // 名字是否存在
int  theme_box_read_file(const char *name, Buffer *out);   // out = {void *bytes; size_t len;}
void theme_box_free_buffer(void *bytes, size_t length);    // 先清零再 free
// 寄存器实测：x0 = name，x1 = &out；内部状态指针自己解析（OnceLock），不用传
```

于是本项目的取字节路径变成 **native 优先**：

1. `SaoqiangWCAssetsNativeAvailable()` — 懒加载 `dlsym(RTLD_DEFAULT, ...)`，
   找不到再 `dlopen(RTLD_NOLOAD)` 试 `/Library/MobileSubstrate/DynamicLibraries/ThemeBox.dylib`、
   `/var/jb/...`、`/usr/lib/ThemeBox.dylib`。
2. `SaoqiangWCAssetsNativeIndex()` — 从 provider **自己的集合**里收名字：
   - 实例：`customThemeFileList`、`themeFileMap`、`currentThemeFileMap`、`currentBubbleFileMap`、`themeDIYFileMap`、`bubbleFileMap`
   - **类方法**（反汇编元类得到的完整名字表，0.11.5 从没查过）：
     `themeFileList`、`currentThemeFileList`、`currentBubbleFileList`、`bubbleFileList`、`themeDIYFileList`
   - 加载器：`themeFiles`、`themeFileMap`、`diyFileMap`、`bubbleFiles`、`iconMaps`
   - `ThemeBoxAssets.themeFiles`、`ThemeBoxIconMap.shared.maps`
   - 收完再逐名调用 provider 自己的 `candidateFileNamesForName:` 展开成 `@2x/@3x`/`.png/.svg` 变体
   - 最后用 `theme_box_contains_file` 过滤，只留真实存在的
3. `SaoqiangWCAssetsNativeRead()` — 按名要字节，拷成 `NSData`，**无条件 `free_buffer`**，
   并加 32MB 上限（与 ObjC 读取通道一致，防止长度字段异常导致巨型拷贝）。
4. `SQFetch()` — native 成功就直出；失败**不当作致命错误**，继续走原来的
   `dataWithContentsOfFile:` 通道（它的错误文本更贴近调用方）。两条通道都失败才计 `skipped`。

### 兜底：`contains_file` 全否时的降级

`contains_file` 可能只认封包内的精确条目名，导致合法逻辑名被一律拒绝。
此时 `NativeIndex` 会把**图片形态的候选名**（图片扩展名或无扩展名，最多 4000 个）带出来，
标记 `unfiltered = YES`，交给 `read_file` 现场判定；失败仍只算 `skipped`，不污染 `missing`。

## 四、保持的安全防护

- 所有 getter 经 `SQMethod` ABI 校验（参数个数 + 返回类型），ivar 读取包 `@try/@catch`，异常即跳过。
- 递归深度 ≤ 4、节点上限 20000、候选先 `minusSet` 权威集合，绝不覆盖已确认的名字。
- 导出的每 64 项做 `SQSameSnapshot` 复核，主题中途变化即中止。
- 单文件上限 32MB；重名（含大小写/Unicode 差异）独立存放，不互相覆盖。
- **不解析、不修改、不上传 `themebox.dat`**；不初始化、不改变 provider 状态，只读调用。

| 字段 | 位置 | 期望 |
|---|---|---|
| `written` | 顶层 | 明显大于上一次 |
| `skipped` | 顶层 | 候选尝试失败数，可大可小，不是错误 |
| `engine` | 顶层 | `new` / `3.0.8` 之类 |
| `native-index` 的 reason | `issues[]` 里 `source == "native-index"` | 关键：新增了多少名字 |
| `ivar-discovery` 的 reason | `issues[]` 里 `source == "ivar-discovery"` | 发现 N 个候选 / M 个合法 |

三个档位的读法：

- **reason 里"新增 300+ 个名字"** → 通杀，说明路线对了，剩下只是覆盖率微调。
- **reason 写成"新增 0 个"**，或整条 `native-index` **不存在** → 说明
  `theme_box_*` 符号没解析到（`Available()` 返回 NO，整段被跳过）。
  这种情况请回一句"没有 native-index 这条"，我就把 `SaoqiangWCAssetsNativeAvailable()`
  的探测结果单独写进 manifest，并换成 hook 变体（挂 `ThemeBoxAssets` 的读文件方法）。
- **reason 里带"contains_file 对全部 N 个候选均返回否"** → 兜底生效了，
  这时 `written` 应该仍然上来了；如果没上来，说明名字本身就不在 provider 手上，
  需要下一步 hook `theme_box_read_file` 记录真实被请求的名字。

阶段1 的 ivar 探查作为兜底保留；若 `native-index` 名字数已接近主题实际图标数，就不用再往下走。

## 七、134 之后：从"发现"转向"范围"（0.11.6）

上一轮把门控拆掉后，导出从 28 涨到 134。134 这个数字本身很说明问题：

`ThemeBoxTheme` 声明了约 50 个图片槽位（`tabBarBG` / `mainBG` / `chatBG` / `inputFullZSBG2` …），
明暗两套就是约 100 个，再加 `ThemeBoxIconMap` 的图标表，正好落在 134 附近。
也就是说 **134 不是"抓到的不全"，而是"一个主题的完整资源集"** —— 加载器只被要求提供当前这个主题的东西，
它给的没错，问的范围本身不对。

所以本轮不再加大"猜名字"的力度，而是同时做三件事：

### 1. 补上两张从没被读过的名字表

| 来源 | 为什么之前漏掉 |
|---|---|
| `ThemeBoxImage.fileMaps / bubbleMaps / diyMaps` | 这是**另一个类**（不是 `ThemeBoxImageLoader`），而且这三个是**类方法**：描述封包，而不是当前主题加载了什么 |
| `ThemeBoxImageMap.devicePrefixMap / deviceTypeMapping / fallbackTypeMap / currentDeviceType` | 设备前缀表。一个按机型出图的封包里，本机只会加载本机那一份，其余只能靠"前缀+名字"反推 |

`ThemeBoxImageMap` 的实现是控制流平坦化的状态机（`udiv` 分发 + `movk` 混淆常量），
静态逆它代价极高，所以**改成运行时读它的返回值并原样写进日志**：
一次导出就能看到封包到底怎么命名，而不是我去假设。

### 2. 问 provider 自己的展开规则

`-[ThemeBoxAssets candidateFileNamesForName:]` 就是主题盒子自己的展开逻辑：
给它一个裸槽位名，它回一组"我会去试的具体文件名"。用它比自己写后缀矩阵准，
因为那是写封包时用的同一张表。拿到的候选仍然逐个 `fileExistsWithName:` 校验 ——
它报的是"会试什么"，不是"有什么"。

### 3. 排除"多主题封包"这个解释

`ThemeBoxInfo` 有 `isParent` 和 `themes`，`ThemeBoxMgr` 有 `localThemes`。
如果当前主题只是一个大包里的一个子主题，兄弟主题的资源根本没被加载，
再怎么探名字也到不了 —— 那是容器问题，不是发现问题。日志里现在有一行直接回答。

### 怎么读这次的日志

`_export-info/issues.txt` 里「清单探测（仅记录，不计入告警）」段，按这个顺序看：

1. `provider-index：新增 N 个资源名` —— 本轮真正多出来的名字数。
2. `Image.xxx=` 与 `UtilClass.xxx=` 各行 —— 哪张表有货、各有多少条。全 0 的那张表就不用再查了。
3. `ImageMap.devicePrefixMap=` —— **这一行最关键**。若是一个非空字典，
   说明封包按机型存了多份，前缀展开就有意义；若是 `nil`，机型假设不成立。
4. `device-variants：前缀 X 个 × 基名 Y → 校验 Z 命中 W` —— W 就是机型变体的实际命中数。
5. `provider-candidates：…` —— provider 自报的候选数和存在数。
6. `theme-set：localThemes=…, isParent=…, 子主题=…` —— 若子主题 > 0，单主题导出天然到不了全部。
7. `container：…` —— 封包字节数与头部。注意：上一轮取证已确认 dat 熵为 8.0、无明文头，
   所以这里出现的头部大概率仍是密文，它的作用是**证明"整包在手上"**，不是提供索引。

### 分支判据

| 现象 | 结论 |
|---|---|
| `device-variants` 命中数百 | 机型变体假设成立，下一版把前缀表当权威清单，不再逐个探测 |
| `ImageMap` 各表皆 nil、`theme-set` 子主题 > 0 | 多主题封包，必须换路线：枚举子主题或找包级索引 |
| `ImageMap` 皆 nil、子主题 = 0、候选也少 | 名字表不在 ObjC 属性里，回到 `ThemeBoxCache.decryptCache` 的真实键去数 |
| N 上千但 `written` 远小于 N | 名字够了、取字节失败，看 `missing` 的具体 reason，收窄 `SQFetch` 的 reader/selector |

### 需要更正的一处旧说法

本文第五节提到的 `contains_file` 兜底**没有接线**。`_theme_box_contains_file` 确实在
`LC_SYMTAB` 里（与 `read_file` 同族），但它的签名未经运行时验证 —— 是否带出参、
返回值是 `int` 还是 `bool` 都只是推测。猜错的代价是崩溃，而 `fileExistsWithName:`
是 ABI 校验过的安全路径，所以存在性判定一律走后者。等某一轮能确认签名再考虑接。

## 八、0.11.6 的日志给出了答案（0.11.7）

### 前缀表被读错了

日志第 5、6 行是这一轮最关键的两个数：

```
ImageMap.deviceTypeMapping={12=5, 12ProMax=6, 15ProMax=8, ...}   ← 设备名 → 枚举
ImageMap.devicePrefixMap={9=a_, 5=p_, 1=x_, 10=mp_, 6=pm_, 2=xr_, 11=mpm_, 7=np_, 3=mn_, 8=npm_, 4=xm_}
```

真正的文件名前缀是 `a_ p_ x_ mp_ pm_ xr_ mpm_ np_ mn_ npm_ xm_`，共 11 个。
上一版把两张表**都**收进了前缀集合，32 个设备名（`11`、`11Pro`、`11ProMax`…）按字典序排在前头，
把 16 个名额全占满 —— 于是 6528 次变体校验全部打在永远不可能出现在文件名里的 token 上，
命中 0 是必然的。

现在只从 `devicePrefixMap` 的**值**取前缀，并单独打一行 `ImageMap 前缀 token（N 个）：…`。
同时把展开的驱动源从「已确认的名字」改成「采集到的槽位」：只以 `x_bg.png` 形式存在的资源，
永远不会以无前缀形式出现，若以已确认集合为基准，就永远不会生成那个唯一存在的形态。
这是同一个错误往上挪了一层。

### 两条不依赖封包"开口"的新路径

它们来自一个观察：已导出的 160 个名字**全部是微信自己的资源名**
（`icons_filled_live@3x.png`、`arrow_left_regular@3x.png`、`wallet_pdd.png`…），
不是主题盒子自造的名字。既然如此，就不必等封包交出名字表。

| 新路径 | 原理 | 失败时会怎样 |
|---|---|---|
| `ThemeBoxMgr` 的分类目录 | `iconPath/maskPath/cardPath/widgetPath/...` 是磁盘上的散装文件，不经封包、不需要名字 | 每个路径单独打一行「图片 N（收录 M）」，不存在就明说 |
| 微信 `Assets.car` | `CUICatalog.allImageNames` 给出候选全集，再问 provider 哪些被替换 | 打一行「CUICatalog 不可用」，静默失败不会伪装成成功 |

两个调用点都做过 ABI 校验，`CUICatalog` 缺失、`initWithName:fromBundle:` 签名不符、
抛异常，一律降级为"没有这个来源"，不会崩。

### 其它变化

- 索引缓存 TTL 2s → 25s。权威 getter 仍然每次快照都重读、仍然是签名的一部分，
  所以中途换主题依然会被发现；重放的只是这份派生名单。
- 名单上限 5000 → 12000（导出侧总上限 19999）。
- `mgr.localCards / localMasks / localBubbles / localVideos` 计数进日志，
  用来判断卡片、蒙版是不是值得追的大类。
- 目录枚举按访问次数（20000）与命中数（3000/目录、6000 总）双重设限：
  一个装满非图片文件的目录不会被走到底，因为这一切发生在主线程。

### 这一轮之后怎么判断还剩多少

按新日志逐条读：

1. `ImageMap 前缀 token（11 个）：a_ p_ x_ mp_ …` → 确认前缀表读对了。
2. `device-variants：前缀 11 个 × 槽位 N → 校验 M 命中 K` → **K 就是机型变体的真实产出**。
3. `asset-catalog：CUICatalog 图片名 N 个 → 校验 M 个变体，封包存在 K 个` →
   这一行的 K 若是几百上千，说明"封包 = 微信资源替换集"成立，路线打通。
4. `目录 iconPath=… 图片 N（收录 M）` 各一行 → 有货的目录会直接体现在 `written` 里。
5. `provider-candidates` / `provider-index` → 变化不大属正常。

若 `device-variants` 的 K 与 `asset-catalog` 的 K 都接近 0，而目录也全空，
那就只剩一种解释：名字表确实只在加密索引里，需要换到 hook 层
（记录 `theme_box_read_file` 实际被请求的名字），这一点在第五节已经预留了位置。

## 九、更正：0.11.7 把多个主题包混在一起导出了（0.11.8 已修）

### 错在哪

0.11.7 假设 `fileExistsWithName:` 回答的是"**当前主题**有没有这个名字"，于是拿微信
`Assets.car` 里两万个名字去逐个问它，命中就收。

这个假设是错的。设备上装了 **4 个**主题包（日志里 `theme-set：localThemes=4`），
`fileExistsWithName:` 是**加载器级**的判断——凡是已加载的包里有的，它都答"有"。
于是那次导出不是"当前主题 + 少量遗漏"，而是**四个主题的并集**。这不是抓漏，是抓串了。

同样的隐患在目录枚举上：`ThemeBoxMgr` 的 `iconPath/maskPath/cardPath/widgetPath`
如果指向多个主题共享的公共目录，枚举它同样会把别人的文件收进来。

### 怎么修的

| 位置 | 处理 |
|---|---|
| 微信 `Assets.car` 强探 | **不再新增任何名字**。改成"抽样测量"：取 300 个当前主题清单里没有的名字去问，统计 provider 仍称存在多少个 |
| 机型前缀展开 | 驱动源从"采集到的全部字符串"退回"当前主题表已确认的名字"——输入收窄 |
| 分类目录枚举 | 只接受**位于当前主题目录之内**的路径，之外的直接跳过并写明原因 |
| 报告 | 新增 `manifest.json` 的 `sourceTally`：按来源统计条目数 |

`sourceTally` 是这次教训的直接产物。几个包混在一起导出时，从外面看就是
"某一个来源的条目数突然变得很大"——这个信号应该能从 `manifest.json` 一眼读出来，
而不是靠读日志里的散文去猜。

### 新的诊断行怎么读

```
asset-catalog：CUICatalog 图片名 4000 个；抽样 300 个本主题清单里没有的名字，provider 仍称存在 287 个 → 存在性判断跨主题生效，不能用来枚举（已停用该来源）
```

最后那个数**不是产出，是判据**：

- 接近 0 → 存在性判断确实不跨主题。这条路以后可以重新启用，但要走"逐主题确认"的形式。
- 大量命中 → 跨主题。这条路永久关闭，同时说明**任何**基于这个名字判断的枚举
  （包括 `candidateFileNamesForName:` 的结果校验）都只能用于"当前主题已有的槽位"，
  绝不能用于发现新槽位。

### 由此得到的结论

"一个导出覆盖 1000 张"这个目标，在当前架构下**不能靠猜名字达成**，
因为唯一能回答"有没有"的接口是跨主题的。要真正做到单主题完整，只有两条路：

1. 找到一个**按主题 id 作用域**的接口（`ThemeBoxAssets.loadThemeAssestFor:` 就是
   按主题加载的，但调用它会改变全局状态，不能在有主题正在用的进程里随便调）；
2. hook 层记录 `theme_box_read_file` 实际被请求过的名字——主题盒子自己渲染时请求过什么，
   就是那个主题真正的资源集合，这是唯一"由 provider 自己给出"的权威清单。

第二条是下一步该走的方向，也是这本说明第五节一开始就预留的位置。

## 十、用字节算账，而不是继续猜名字（0.11.10）

### 已经确定的事实

用户把 `themebox.dat` 本身发过来了，于是这件事第一次可以按字节核对：

| 量 | 数值 |
|---|---|
| 封包 | 10,917,408 字节 = 10.41 MB |
| 已导出主清单 | 3,140,031 字节 = 28.8% |
| 差额 | 7,777,377 字节 |
| 本主题已导出资源均值 | 859,028 / 90 = 9,545 字节 |

前几轮我按 30 KB/张 估算，说过"11 MB 装不下 1000 张"。**这个估算是错的**，
实测均值只有 9.3 KB，所以差额对应约 **814 个**条目，合计约 904 项——
用户说的"至少 1000 张"方向是对的。

同时封包本身已被独立测量确认是不透明的：熵 8.0000 均匀、无重复的 16 字节块、
没有 PNG/ZIP/GIF/RIFF 魔数、16 字节对齐。也就是说密钥只在运行中的 provider 里。

### 因此这一版要回答的问题

`fileExistsWithName:` 已实测是**跨主题**的（本主题清单外 300 个名字，provider 仍称
存在 60 个，20%）。既然名字来源不可信，唯一还能当判据的就是**体积**：
10.4 MB 的封包装不下 40 MB 的资源。

所以 0.11.10 把探测项改成**只读不存**，`issues.txt` 第一段就是这一行：

```
封包覆盖率：主清单 3140031 字节 = 封包的 28.8%；探测命中 N/M 项共 X 字节，两项合计 Y 字节 = Z%
```

（`N/M/X/Y/Z` 是每次导出当场算出来的，不是写死的。）

- 合计接近 100% → 这些探测项确实就是本主题没被列出的资源，下一步按字节对账导出。
- 合计远超 100% → 探测项来自别的已装主题，此路彻底关闭，只能走下面第二条。

探测有硬上限（6000 次读、或累计到封包体积、或 20 秒），所以它不会让导出变慢到不可用，
也绝不会把别人的图写进导出目录——上一轮混主题，正是"读到了就存下来"造成的。

### 同时试的一枪：封包自己的文件表

封包的索引必须是 provider 能解析的某个条目。于是用同一套 `theme_box_read_file`
去试 32 个常见清单名（`theme.json`、`index.plist`、`manifest.json`、`filelist.plist`…），
判据是**内容**而不是名字：文本/JSON/二进制 plist 才算表，图片魔数一律不算。

命中就存成 `_export-info/pack-index.bin`（在 `manifest.json` 里声明 `packIndexBytes`）。
只要有这一张表，就能一次列全，不需要再猜。没命中也是一条明确结论：
表不是可单独寻址的条目。

### 这一版没做的，和为什么

hook `theme_box_read_file` 记录"provider 实际请求过的名字"是路线二，也是最终形态。
它需要 `method_exchangeImplementations` 级别的改动，风险与本版的字节对账无关；
把两件事放进同一次编译，一旦崩溃就同时失去诊断数据。所以先出这一版。

## 十一、用户给的样本包，直接指出两个错（0.11.11）

样本 `空耳奶白拟态.zip` 解压后：

| 项 | 数值 |
|---|---|
| 文件 | 2,503（2,500 PNG + `weui_color.xml` + `weui_color_new.xml` + `color.css`） |
| 去重后的基名 | **717** |
| 形态 | `@2x.png` 601 / `@3x.png` 632 / `_Dark@2x.png` 581 / `_Dark@3x.png` 623 |
| 解压总字节 | 19,464,761（均值 7,777 B/张） |

也就是说一个正常封包是 **717 个基名 × 4 种形态**，不是 134 个"槽位"。

### 错一：我把装图的那个目录整个跳过了

上一轮 `issues.txt` 自己写着：

```
目录 iconPath=.../Documents/ThemeBox/Icons 在当前主题目录之外（共享或其他主题），跳过
目录 maskPath=.../Documents/ThemeBox/Masks ... 跳过
目录 cardPath=.../Documents/ThemeBox/Cards ... 跳过
目录 widgetPath=.../Documents/ThemeBox/Widgets ... 跳过
目录 currentThemePath=.../Themes/冰箱贴 图片 2（收录 2）
```

`Themes/冰箱贴` 里只有 `cover.png` 和 `icon.png` 两张，因为真正的图片放在
`ThemeBox/Icons`、`Masks`、`Cards`、`Widgets` —— 引擎给当前主题用的那份图片库，
和 `Themes/` 平级而不在主题目录里面。

0.11.8 为了阻止混主题，加了"不在主题目录内就跳过"的规则。规则没错，**但把这一类目录
一起误伤了**：`themePath`/`bubblePath`（`Library/Preferences/ThemeBox/Theme`）才是
"多个主题共用的仓库"，必须跳；`Icons` 这类分类目录是当前主题的图片本身。

0.11.11 的规则：

| 路径 | 处理 |
|---|---|
| 在主题目录内 | 递归读（不变） |
| 末段就是本主题名（`diy/<主题>`） | 读 |
| 共享目录下有本主题名的子目录（`Icons/<主题>`） | 只读那个子目录 |
| `iconPath`/`maskPath`/`cardPath`/`widgetPath` | **扁平读**，不递归，日志标注"分类目录扁平读取" |
| `themePath`/`bubblePath`/`baseThemePath` | 仍然跳过（这几个确实装着多个主题） |

不递归是有意的：分类目录里若真有按主题分的子目录，递归等于把别的主题拉进来。

### 错二：只问了一种形态

`@3x`、`@2x`、`_Dark@3x`、`_Dark@2x` 各占约四分之一。之前的候选只生成 `@3x` 和裸名，
**`@2x` 全部、Dark 全部根本问不到** —— 即使名字已在主题表里确认过也一样。
0.11.11 补齐四种形态（外加 `.svg`），并把目录探测也改成六种形态：
统计的是"有多少个基名存在"，可以直接和 717 对照。

### 这一轮该看到的数字

`issues.txt` 里应出现：

```
目录 iconPath=.../Icons 图片 N（收录 N，分类目录扁平读取）
```

N 若接近 700，就是拿到了整套图标；若接近 0，说明引擎并不在磁盘上摊开，
必须回到"hook provider 的读取请求"那条路（见第十节）。

## 十二、轻颜的导出清单是这次的关键证据（0.11.12）

第二份样本 `轻颜.zip` 里带了一个 `_export-info/manifest.json`，**是同一个工具导出的**：

```
清单 2525 · 已导出 2525 · 未取得 0 · 失败 0
themeName = 轻颜 2024
provider  = ThemeBox + current enabled BubbleBox
items     2525 条，key 全是裸文件名：2016_coin1.png / 128b4573….svg
```

也就是说 2525 张是**做到过的**。但它和现在这台设备有两点不同：

1. 那次 `scope` 写的是"当前主题已加载索引、DIY覆盖和已启用独立气泡资源"，
   没有"3.0.8运行时已解密缓存"—— 说明那台/那次是**旧引擎、主题已解压铺在磁盘上**，
   `themeFiles` 里就是完整的 2525 条；
2. 现在这台是 3.0.8 新引擎，主题被打成加密的 `themebox.dat`，
   ObjC 侧的表只剩 `themeFileMap=0`、`UtilClass.themeFileList=2`、`IconMap.maps=133`。

所以 112 不是"抓错了地方"，是**新引擎把清单挪进了解密域内**，ObjC 表不再持有它。

### 为什么按名字解封包是安全的

`theme_box_read_file` 是 Rust 侧的函数，它只认识**已经加载进内存的那个容器**
（`theme_box_read_file` 的桩代码把全局单例作为隐藏参数传进去）。别的已装主题
不在这个容器里，所以拿别的主题的文件名来问，它返回空。

由此得到两件事：

- 名字不构成污染。候选表再长，读不出字节就是没有 —— 0.11.7 混包的成因是
  `fileExistsWithName:`（跨主题）加共享目录枚举，不是这条路径；
- 命中总量天然受封包体积约束。读到的字节加起来不可能超过 `themebox.dat` 的大小，
  这就是自检：总量贴着封包走，说明拿全了。

### 候选表从哪来

`SaoqiangWCAssetsPackNames.m` 里内嵌 2,602 个基名，取自这两份样本的并集
（轻颜 2478 + 空耳 703，重叠后 2602）。运行时按 9 种形态展开
（`@3x.png`/`@2x.png`/`.png`/`_Dark` 三种/`.svg` 三种）≈ 23,000 个候选，
按"最可能先命中"的顺序问，命中字节累计到封包体积的 102% 就停。

上限：40,000 次询问 / 90 秒 / 封包体积，任一到达即停并在报告里写明。

### 这一轮的报告该长什么样

```
按名字扫描封包：候选 23418 个，实际询问 N 个，命中 H 项共 B 字节（封包 10917408 字节）
封包覆盖率：主清单 … 字节 = 封包的 …%；探测命中 …
```

`B` 接近 10,917,408 就是全了；`H` 若还是 100 出头，说明这台设备的主题用的名字
不在这两份样本里，那就把 `_export-info/issues.txt` 发我，我按实际命中的名字反向补表。

## 十三、第一次只抓一点、第二次才全（0.11.13）

用户反馈：点第一次只抓到一点，点第二次才全。原因是本工具自己造成的，两处：

### 一、导出被自己的读取判成"主题变了"

`SQSameSnapshot` 每导出 64 项就重跑一次快照，比对签名，用来防止导出中途换主题。
但 0.11.12 按名字解包会**真实地改变 provider 的状态**——解出来的东西会进
`decryptCache`、`themeFileMap` 之类。于是签名变了，检查判为"主题或资源清单在导出中变化"，
导出在中途收摊。第二次点时缓存已经是热的，签名稳定，所以一次到底。

修法：加 `SQSnapshotStill(initial, &fresh, error)`，允许把**新一轮快照本身**取回来。
按名字扫描结束后，用新快照替换比对基线（前提是 `loader` 指针与 `themeID` 没变，
真的是换主题仍然会判失败）。`manifest.json` 里记 `packNamesRebased`。

### 二、冷启动时 provider 还没热

第一次读会触发容器初始化，比后续读贵得多。0.11.13 在计时之前先做一次预热读，
把这份开销挪出扫描窗口；扫描本身改成最多三轮，某一轮一项都没命中就隔 0.8 秒再来一次
（冷的第一次空手而归、第二次全中，正是用户手点两次的现象）。

上限：240 秒总预算、命中字节到封包体积 110% 即停。

### 新日志

```
按名字扫描封包：候选 23418 个，询问 N 次、2 轮（第1轮 …，第2轮 …），
命中 H 项共 B 字节 / 封包 10917408 字节（98.4%），预热 820 ms
```

`第1轮/第2轮` 分开记，一眼能看出是"一轮到底"还是"需要第二轮补"。正常应该一轮就到底。

## 十四、"命中几百张，但保存不了"（0.11.14）

这是 0.11.13 没修干净的地方。0.11.13 在扫描后重设了一次基线，但**写文件本身**
也会动 provider：那 112 项里有相当一部分是走 ObjC 读取器拿的（`dataForFileName:`、
`getThemeFile:`），这些读会往 `decryptCache`/`themeFileMap` 里继续塞东西。
于是写到第 64 项时签名又变了，导出继续被自己判成"主题变了"而中止 ——
中止即 `available=NO`，所以"命中几百张但按钮点不动"，第二次缓存热了才一次过。

### 改法：写文件阶段只比身份，不比签名

```objc
static BOOL SQSameTheme(...)   // loader / bubbleLoader / themeID / root
```

签名里包含 provider 的缓存内容，而这个导出**故意**在改它，用它做中途校验本身就是错的。
真正需要防的是"导出中途换了主题"，那件事一定体现在 loader 指针、themeID 和主题根目录上。
开工前那一次校验仍然用完整签名（那时还没读过任何东西，严格比较是准确的）。

### 另一处：核对阶段读第二次

`SQFetch` 重读用来确认"源没变"，但 provider 是从正在被填充的缓存里作答的，
偶尔一次读会落在刷新中间。现在遇到不一致会**立刻再读一次**，两次里有一次对上就通过；
两次都不同才是真的变了。

### 该看到的现象

- 第一次点击：扫描完后进度直接走到底，按钮可点；
- 若 UI 仍报错，把报错原文发我 —— 现在剩下的失败原因一定带具体文案
  （`原资源在导出中变化` / `主题被切换` / `读取器未返回原始NSData`），
  一句就能定位，不用再猜。

### 补充：稳定签名

只比身份还不够。`source-color-mutation` 这个既有检查要求"导出中颜色表被改必须中止"，
而颜色表不在身份里。所以 `SQSnapshot` 现在多输出一个 `stableSignature`，
只覆盖**这个导出改不动**的东西：

- `root` / `themeID` / `engine`
- `companions`（`weui_color_new.xml`、`color.css`、`themebox.dat` 的 size/inode/mtime）
- `container`（尺寸与对象指针）

写文件阶段比 `stableSignature`，不碰 `signature`。这样：

| 情况 | 结果 |
|---|---|
| 本工具解包、写文件填了 decryptCache | 不中止（稳定签名不变） |
| 导出中颜色表被改 / 主题文件换掉 | 中止（companions 变了） |
| 导出中切换主题 | 中止（loader / themeID / root 变了） |

## 十五、注入后卡顿：来源与改法（0.11.15）

### 结论先说

卡顿不是"钩子太多"，而是**主线程上反复做同一件事**。三处：

| 位置 | 原来 | 频率 | 代价 |
|---|---|---|---|
| 页面采样定时器 | `NSRunLoopCommonModes` + 0.8 s | 滚动中照样触发 | 每 0.8 s 递归遍历整个窗口（预算 1600 个 view） |
| `-[CommonMessageCellView layoutSubviews]` | 每个可见 cell 每次布局 | 滚动帧级 | 每次从 cell 往下走 32 个 view、逐层 `convertRect` |
| `+[UIImage imageNamed:]` 等钩子 | 每次图片加载 | 每帧几十次 | 每次约 15 个 `NSString` 分配 + 3 次 `@synchronized` |

`UITableView` 滚动时三者叠在一起，主线程一帧里既有全窗口遍历，又有逐 cell 的气泡遍历，
还有每次 `imageNamed:` 的字符串分配 —— 这就是"点着有点卡"的实测来源。

### 1. 采样定时器只在不滚动时跑

`UITrackingRunLoopMode` 属于 common modes，所以 common-mode 的定时器**会在滚动中触发**。
把它挂在 `NSDefaultRunLoopMode`：滚动期间不触发，手一停立刻补一次，看到的正是用户滚到的那一屏。
再按上一轮耗时自适应：

```objc
CFAbsoluteTime cost = CFAbsoluteTimeGetCurrent() - started;
SaoqiangWCAssetsPageNextAllowed = now + (cost > 0.012 ? 2.4 : (cost > 0.005 ? 1.6 : 0.8));
```

遍历便宜就 0.8 s 一次，贵就退到 2.4 s 一次。`tolerance = 0.4` 让系统能和其他定时器合并唤醒。

### 2. 气泡视图：内容没变就不重走

`layoutSubviews` 是帧级的。给被观察的 view 挂一个记录（`contents` 指针 + 时间 + 上次是否命中）：

- `contents` 没变且**上次命中了** → 直接返回（已经抓到的字节没理由再走一遍）；
- `contents` 为空或上次没命中 → 最多 1.5 s 重试一次。

只在"指针没变"是**可证明**的情况下做永久跳过，其它情况一律退化成限流，不会漏抓。

### 3. 名称判定不再分配对象

`UIName` / `BubbleName` / `SafeRendererName` 每次图片加载都要跑。原来每个名字要：

```
lastPathComponent → lowercaseString → 11 次 containsString → 2 个 NSArray 字面量
→ pathExtension → 4 次 stringByReplacingOccurrencesOfString
```

现在走 `SaoqiangWCAssetsNames.h` 里的 `static inline` 字节比较（全 ASCII，UTF-8 原样拷贝不截断），
外面再套一层 4096 条的判定缓存（`os_unfair_lock`）：稳定状态下就是**一次加锁 + 一次字典查找**。
判定是纯函数，缓存不会过期。

### 4. 其余几处

- `SaoqiangWCAssetsCallNamedSource`：没有任何外层观察、名字也不可记录时直接调原实现，
  不再 new 一个 scope 对象 + block + 换 TLS。这是微信自己加载 UI 图片的绝大多数情况。
- `OwnUIActive()`：每次钩子都会问。改成先读一个原子计数（几乎总是 0），命中才去读那两个 weak 引用。
- `ImageForLayer`：原来每次都要扫一遍最多 512 个已知图片。带名字的 backing 记录已经是权威答案，直接短路。
- `ThemeDidCall`：每次被观察的调用都 `@synchronized` + 写字典。改成安装钩子时分配下标，调用时一条原子自增。
- `ThemeLooksLikeImage`：原来对非 PNG/JPEG 的数据都要把前 8 KiB 解成 `NSString` 找 `<svg`；改成字节扫描。
- `CommonMessageCellView` 的 `NSClassFromString` 从"每个 view 每次"改成缓存一次。
- 悬浮按钮的 0.5 s 定时器：改成 1 s + `tolerance`，只在 default mode 跑，且 `hidden` 值没变就不写
  （给 `hidden` 赋同样的值仍会让 layer 变脏）。

### 抓取完整性没有降低

这些改动只减少"重复做同一件事"，不改变任何判定：

- 滚动中不采样，但松手后立刻补采，屏上的东西一样会被看到；
- 气泡只在内容真的变了才重走；
- 名称判定结果逐条等价（同一份坏词表、同一份前缀/后缀规则）；
- 导出引擎（`ThemePack`）没有改动。

## 十六、入口改到「插件」列表（0.11.16）

悬浮按钮去掉了。它的问题不只是挡视线：作为 key window 的子视图，每次出现都要
`bringSubviewToFront`，还要一个定时器盯着自己的显隐。

现在入口是微信「插件」页里的一行：

```
插件
 └ 主题盒子   3.0.8 ›
 └ WCRefine   2.1-9 ›
 └ 小勾引  0.11.16 ›      ← 追加的一节
```

那一页是别的注入提供的，**我们对它一无所知**，所以做法是运行期认页、认表，不改它的模型：

1. `-[UIViewController viewDidAppear:]` 上挂一次 swizzle，只做标题比较
   （`插件` / `第三方插件` / `微信插件`，最多看三层 parent）；
2. 命中后找视图层级里第一个 `UITableView`；
3. 用一个**数据源代理**接替 `table.dataSource`：把原来的对象弱引用住，
   未知方法走 `forwardingTargetForSelector:`，`numberOfSections` 返回原值 +1，
   多出来的那一节只有我们一行。原有 section / row 的下标一个都没动，
   所以别的插件那一行照样能点。
4. 选中与行高在**代理类的类**上加一次实现（`class_addMethod`，失败才
   `method_setImplementation`），只对 `indexPath.section == 我们这一节` 生效，
   其余原样转回它自己的实现。
5. 找不到表（那一页是 collection view 或自绘）就退到导航栏右侧放一个「小勾引」按钮，
   不占右槽就放弃，绝不覆盖别人的按钮。

点这一行调 `SaoqiangWCAssetsPresentPanel()`，和原来的面板是同一套代码。

那一页每次 `viewDidAppear` 都会重新认一次表：如果宿主把 `dataSource` 换成了新对象，
我们只更新代理里的弱引用、再把代理装回去，不重建、不重复加类方法；代理存在且仍装着
就什么都不做。整条路径只在出现页时跑一次，不在滚动或布局路径上。

## 十七、第二轮掉帧优化

0.11.15 之后还剩两处每帧成本：

| 位置 | 原来 | 现在 |
|---|---|---|
| `-[CommonMessageCellView layoutSubviews]` 的观察块 | 每次布局都 `class_getInstanceMethod` + `NSMethodSignatureWithObjCTypes`（微秒级） | 按**实例类**缓存 getter IMP，滚动稳态是一次指针比较 |
| 三个 `UIImage` 钩子 | 每次调用都有 `@try/@finally` 异常帧 | `__attribute__((cleanup))` 代替，展开时同样会跑清理 |
| 解码图片 | 每张（含所有头像）都进全局锁查一次 | 全局计数为 0 时直接返回，不加锁 |
| 气泡观察 | 每次布局都取 `CFAbsoluteTimeGetCurrent()` | 内容指针没变且上次命中时只比指针 |

`NSMethodSignature` 那条是大头：它每次都会解析类型编码并新建对象，
而 `layoutSubviews` 是帧级的、每个可见 cell 一次。

## 十八、总开关（0.11.17，小扒手）

插件不常用，所以注入后常驻的那点开销也不该一直付。0.11.17 加了一个持久化总开关，
默认**关闭**。dylib 仍然注入、入口行仍然在「插件」列表里，但关闭时所有钩子
在第一条指令就转回原实现。

开关放在面板顶部：「总开关（关闭时不抓取，几乎无开销）」。列表里那行右侧也会显示
`0.11.17 · 总开关开/关`，回到插件页就能看到状态。开启后立刻采样当前页，不需要重装
或重启微信。状态存在 `NSUserDefaults` 的 `SaoqiangWCAssets.master.v1`，
在 `SaoqiangWCAssetsInstallImageHooks()` 里读一次，之后只读那个 relaxed atomic。

关闭时各热路径的代价：

| 位置 | 关闭时的行为 |
|---|---|
| `+[UIImage imageNamed:]` / `inBundle:` / `imageWithContentsOfFile:` | 一次 relaxed load，直接调原 IMP；不建 scope、不建 block、不动 cleanup 计数器 |
| `+[UIImage imageWithData:]` / `initWithData:` 等 | 同上，不进关联表、不取全局锁 |
| `resizableImageWithCapInsets:` 等传播钩子 | 原实现照常执行，只跳过元数据传播 |
| SVG / ThemeBox 命名钩子 | 直接调原实现，不建 SVG scope、不解析类型、不写调用计数 |
| `-[CommonMessageCellView layoutSubviews]` 等气泡钩子 | 一次 load 后返回；不遍历图层、不读时钟、不分配访问记录 |
| 页面采样定时器 | 定时器还在，但只有一次 load；不读时钟、不遍历窗口 |
| 「插件」列表入口 | **不关**，否则就没有打开开关的地方；只在页面出现时跑一次 |

关闭开关不会清空已经抓到的记录，面板照样能查看和导出。它只是不再新增抓取。
「开始/停止」按钮在总开关关闭时置灰，避免用户以为抓取已经开始。

测试宿主（`SAOQIANG_WCASSETS_TESTING`）默认把总开关设为开，所以原有的导出、
命名、引擎检查仍然走完整路径；`tests/UIDemo.m` 里额外做了关→开的往返检查，
确保开关只是门控，不会破坏已安装的钩子。

## 二十、真机反馈修正（0.11.19）

0.11.18 在真机上暴露两个问题，都是面板/状态同步的错，与抓取引擎无关：

1. **开关看不见**：三个 `UISwitch` 只给了 trailing + centerY 两个约束，
   靠 `intrinsicContentSize` 撑尺寸。真机注入环境下这个 intrinsic size
   不可靠，宽度变成 0，于是整行只剩标题。现在每个开关都补上
   `width=51 / height=31` 的显式约束，并标记为自有视图，
   使用的仍是微信原生 `UISwitch`（与主题盒子 3.0.8 设置页同一控件；
   它走 `WCTableViewCellManager switchCellForSel:target:title:on:`，
   内部就是 `UISwitch`，只额外改了 `thumbTintColor`）。
2. **升级后什么都不抓**：开关状态存在 NSUserDefaults，升级后仍是「开」，
   但 store 的 `_enabled` 每次启动都从 NO 开始。0.11.18 删掉了「开始」
   按钮，而 `SaoqiangWCAssetsSyncCapture()` 只在拨动开关时调用，
   导致开了开关却从未把 store 打开。现在 `SaoqiangWCAssetsInstallUI()`
   在启动时调一次同步，开关状态直接决定 store 的抓取状态。
3. **分类被置灰**：分段控件和「抓取主题」按钮原来跟着功能开关置灰，
   导致已抓到的记录反而看不了。现在它们只受 `busy` 约束，
   随时可点；开关只管抓不抓，不管看不看。

## 三十二、修复 WCRefine 插件收纳闪退：改用 ThemeBox 式原生注册（0.11.31）

- 真机反馈：0.11.29/0.11.30 把「小扒手」插进 WCRefine 插件收纳的
  同一 section 后，整个插件收纳页闪退，而且宿主 cell 的白色线框被压住。
- 根因定位：
  - 这两版直接把我们的行追加进宿主 `injectSection`（`numberOfRows` +1），
    并在 delegate 类上 swizzle `didSelect` / `height` / `estimatedHeight` /
    `willDisplayCell` / `didEndDisplayingCell` 五个方法。
  - WCRefine 插件收纳页有自己的 item 模型/分组/复用逻辑；只改 tableView
    的 section/row 数而不改它的数据源模型，未被 hook 覆盖的回调会把
    indexPath 当成宿主模型下标访问，导致越界/类型不匹配而闪退。
  - 我们跳过宿主的 `willDisplayCell` / `didEndDisplayingCell`，宿主就无法
    完整配置圆角卡片和白色线框，所以出现“压住白色线框”的视觉问题。
  - 结论：tableView 插行方案本身不可靠，颜色补偿只是掩盖症状。
- 对照用户提供的 `主题盒子3.0.8_roothide（隐根）(1).deb` 与本地
  `WCRefine_2.1-8_隐根.deb`，静态分析确认：
  - ThemeBox 二进制只引用一个注册选择器
    `registerControllerWithTitle:version:controller:`，并没有 hook
    WCRefine 插件页 tableView。
  - 该方法由 `WCRefinePluginHubManager` 的**实例**实现（类方法
    `sharedInstance` 取单例），类型编码 `v40@0:8@16@24@32`。
  - WCRefine 内部会把 `controller` 参数当 NSString 处理
    （`isKindOfClass:` + `stringByTrimmingCharactersInSet:`），
    因此传控制器类名字符串即可，而不是 UIViewController 实例。
- 本版改动：
  - 完全移除 0.11.29/0.11.30 的 `injectSection`、同 section 插行、
    宿主行背景读取，以及新增的 3 个 delegate hook；恢复 0.11.26
    已验证稳定的“追加独立 section + 仅 hook didSelect/height”回退路径。
  - 新增 `SaoqiangWCAssetsRegisterInPluginHub()`：用 NSInvocation 安全调用
    `[[WCRefinePluginHubManager sharedInstance] registerControllerWithTitle:
    version:controller:]`，参数为「小扒手」、当前版本号、
    `NSStringFromClass([SaoqiangWCAssetsController class])`。
    WCRefine 不存在、API 变更或抛异常时静默返回 NO，不影响其它功能。
  - 注册时机：注入后 1 秒主线程尝试一次；进入插件页时再尝试一次。
    一旦注册成功即置位，插件页完全跳过 tableView 回退路径，
    因此不会重复出现两行，也不会再碰宿主索引和白色线框。
  - 未注册成功时仍保留原来的独立入口行（在收纳框外但可点开），
    这是“不闪退优先”的兜底。
- 真机验证重点：打开 WCRefine 插件收纳页不再闪退；「小扒手」以原生
  插件条目显示在同一卡片内；白色线框完整；点击能打开面板。

## 三十八、修复全局手势不生效：改到事件层检测（0.11.37）

- 真机反馈 0.11.36 双指/三指长按完全呼不出页面。
- 根因推断：`SaoqiangWCAssetsKeyWindow()` 在 dylib 早期安装时拿不到 keyWindow
  （scene 未 active / window 尚未成为 key），而 `UIWindowDidBecomeKeyNotification`
  的注册可能晚于窗口变 key 的时机，导致手势从未挂上；即使挂上，
  window 级手势也容易在微信自身手势竞争中被压制。
- 修复：放弃 window 手势，改为 hook 事件入口 `sendEvent:`，在事件层自行检测：
  - 同时 hook `-[UIApplication sendEvent:]`（应用实际类，兼容 UIApplication 子类）
    与 `-[UIWindow sendEvent:]`，两层互补：前者保证任何事件都经过，
    后者保证触摸已绑定 window、`locationInWindow` 坐标有效。
  - 检测器按「活跃手指数」跟踪：2 指 / 3 指时记录起点并起 0.55s 定时器；
    定时器到点若手指数未变、未移动超 30pt、未触发过，则呼出对应页。
  - 静止时系统不再派发 touch 事件，故必须用定时器确认长按（不能只靠后续事件）。
  - 手指抬起（Ended/Cancelled）即重置，所以短按、点击、双指缩放（移动超阈值）都不会误触。
  - 原实现始终先 `SaoqiangWCAssetsSendEventOriginal` 调用，绝不吞事件；
    检测器对同一触摸序列幂等，两层 hook 重复看到同一事件也不会双触发。
  - 面板已显示（`SaoqiangWCAssetsOwnUIActive`）时忽略。
- 2 指 → 图标页，3 指 → 主题页；present 完成后下一 runloop turn 切页。
- 版本号 0.11.37；CI 构建验证。

- 手势归属：只接管竖向拖拽；落点在 `UIScrollView`（列表、工具页）里时

- 另外在导航栏右侧加了一个 `chevron.up/down` 按钮，一键在两档之间切换，
  避免只有"知道要拖标题栏"的人才会用。
- 关闭路径（‹ 首页、右上角、返回微信首页）统一走
  `SaoqiangWCAssetsDismissTarget`：有卡片时关卡片，没有时关自己，
  保证卡片模式下也能退干净。
- 插件收纳页的入口**不变**（仍全屏 push），只有双指/三指长按走卡片。

### 2. 抓取图标名称页加统计条

- 位置：分段筛选器下方、"清空"按钮那一行之前。
- 内容：四个等宽列 —— 总数 / PNG / SVG / 原生，数值 17pt 等宽数字 + 10pt 说明。
- 数据口径与"当前"列表一致：遍历 `[store SaoqiangWCAssetsSnapshot]`，
  只统计 `SaoqiangWCAssetsIsCurrent(record, runtimeID)` 为真（本次运行、跨页累计）
  的记录，所以 总数 恒等于列表不筛选时的行数。
- 原生沿用 `SaoqiangWCAssetsIsNative()`：非 SVG、有原始资源名、来源是
  `UIImage imageNamed:` / `imageWithContentsOfFile:` / `initWithContentsOfFile:`。
- 为在 3/5 高度里省出纵向空间，统计条高 46pt、清空按钮压到 32pt，
  标题上边距 16→12、按钮行间距 20→14。
- 版本号 0.11.40；CI 构建验证。

## 四十二、页面标题被导航栏压住 / 图标抓取与名称补全（0.11.41）

### 1. 页面标题被导航栏挡住

- 现象：卡片形态呼出后，「抓取图标名称」「抓取主题」两行标题只露出下半截，
  像被导航栏盖住；列表最后一行也会被屏幕底边切掉。
- 根因：三个页面原来钉在 `self.view.safeAreaLayoutGuide` 上。0.11.40 把面板的
  导航控制器放进卡片子容器后，导航控制器传给子控制器的安全区不再包含导航栏
  （实测 top/bottom 都变成 0），页面内容就从导航栏底下开始了。
- 修复：三个页面统一放进一个 `pagesHost` 容器，容器的上/下约束常量在
  `-viewDidLayoutSubviews` 里按真实几何重算：
  - 上 = `max(safeAreaInsets.top, 导航栏在 self.view 里的底边)`，再 +2pt 余量；
  - 下 = `max(safeAreaInsets.bottom, 窗口底部安全区 - 页面溢出部分)`。
  无论全屏 push 还是卡片呈现、无论安全区是否被正确传递，标题都不会再被压住。

### 2. 当前页面很多图标抓不到

- 0.11.40 的采样器对「没有名称元数据的图片」要求祖先里必须有 `UIButton`，
  所以设置行、自定义 cell、tab 条里用普通 `UIImageView` 画的图标全被跳过。
- 现在改为：小尺寸（≤72pt / ≤288px）、视图 ≤120pt、不在照片/头像/表情/朋友圈
  等类名黑名单里、且不是圆形（圆角 ≥ 短边 45%，用来排除头像）的图片都收。
- 另加图层兜底：有些图标根本不生成 `UIImage`，直接写进 `layer.contents`
  （字形/SVG 渲染）。以前只接受钩子见过的 CGImage，其余直接跳过；现在对
  ≤320px、长宽比 0.25–4、视图 ≤160pt 的 `layer.contents` 直接快照成像。
  同一个 layer 的 UIImage 会关联缓存，重复采样不会重复入队。
- 采样间隔 0.8s → 0.4s，退避阈值同步放缓；待处理队列 16 → 32，
  面板关闭后立即补采样一次（面板开着时采样是被禁止的，所以点了「开始抓取」
  之后必须等关掉面板才会真正采到东西）。

### 3. 抓到的图标没有名称

- 两个原因：
  1. 图标在点「开始抓取」之前就已经解码并缓存，之后不会再有加载调用，
     钩子自然拿不到名字；
  2. `SaoqiangWCAssetsUIName` 只认 `icons_` / `_regular` / `_heavy` /
     `fileicon_` / `tabbar_` / `navigationbar_` / `badge` 这几种前缀后缀，
     其余命名（含真实图片文件名）一律丢弃。
- 修复：
  - 新增 `SaoqiangWCAssetsRecoveredImageName()`，用 KVC 读取 UIImage 及其
    `imageAsset` 的私有名称 ivar（`_imageName` / `_assetName` 之类，键名只取
    以 `name` 结尾的对象 ivar），按 `SaoqiangWCAssetsSafeRendererName` 同一套
    规则校验后使用，并缓存到该 UIImage 上；读的是 KVC 不是裸 ivar 内存，
    weak 槽位也安全。这样已缓存的图标也能恢复成真实资源名，来源标注
    「UIImage imageNamed: · 名称从已缓存图片恢复」，计入「原生」。
  - `SaoqiangWCAssetsUIName` 增加两条放行：带图片扩展名的真实文件名、
    stem 中含 `icon` 的资源名。
- 名称后到时记录会自动升级：同一个 image 的 info revision 变化会让
  signature 改变，Store 用 captureKey 原地替换旧记录，不会留下两条。

## 四十三、标题仍被导航栏切一半 / 图标名称全空（0.11.42）

### 1. 页面标题还是被挡住（0.11.41 没修好）

- 现象：卡片呼出后「抓取图标名称」「抓取主题」只露出下半截，红色圈出来那块
  正好卡在导航栏底边。
- 0.11.41 的做法（`max(safeAreaInsets.top, 导航栏底边) + 2`）为什么没用：
  卡片里导航控制器是子控制器，**在较老的 iOS 上导航栏是懒创建的**——
  第一次 `viewDidLayoutSubviews` 时 `self.navigationController.navigationBar`
  可能还是 nil 或 zero frame，于是只拿到 `safeAreaInsets.top`（状态栏那 20pt），
  页面容器被放在 22pt 处；随后导航栏才建出来并盖住 0~44pt，
  正好把 34~56pt 的标题切掉一半。模拟器（iOS 26）导航栏建得早，
  所以 CI 的数值断言是通过的，真机才暴露。
- 修复：不再自己算数，改成**约束到导航栏本体**——
  在 `-viewDidLayoutSubviews` 里装一条必选的
  `pagesHost.top ≥ navigationBar.bottom + 10`（两视图在导航视图里同源，
  Auto Layout 可跨层级求解），另加 `pagesHost.top ≥ self.view.top + 6`，
  原来那条等于约束降为 `UILayoutPriorityDefaultLow` 只做定位偏好。
  导航栏什么时候建出来都不影响结果，`-viewWillAppear:` 里再
  `setNeedsLayout` 一次兜底。
- 同时把卡片里自建的导航栏设为**不透明**（`translucent = NO` +
  `UINavigationBarAppearance configureWithOpaqueBackground`，底色用面板画布色），
  内容不可能再从栏底下滑过去。

### 2. 抓出来的图标名称全是「无原始资源名」

- 根因：这些图标**根本没有 UIImage**。微信把「服务 / 收藏 / 二维码」这类小图标
  直接画进 `layer.contents`，采样器只能拿到裸 CGImage 并快照成像；
  而 `SaoqiangWCAssetsRecoveredImageName()` 读的是 UIImage 的私有名称 ivar，
  对刚从 CGImage 造出来的新对象必然为空。于是每一行都是「无原始资源名」。
- 修复一（精确匹配）：新增 CGImage → 资源名备忘表。
  `imageNamed:` / `imageNamed:inBundle:` / `imageWithContentsOfFile:` /
  `initWithContentsOfFile:` 的钩子**在抓取开关关闭时也记录**
  （限制 256px 以内、160 条 / 8MB 上限、CGImageRetain 保证地址不复用），
  图层快照时按 CGImage 指针精确匹配，命中即用真实资源名。
  这解决了「图标在点开始抓取之前就加载完了」这一类。
- 修复二（界面取名）：指针匹配不到时，读所在控件的信息——
  `accessibilityLabel` → `UIButton.currentTitle` → `UILabel.text` →
  **同行相邻的 UILabel**（必须几何相邻：垂直中线差 ≤ 图标高度、
  水平间距 -4~64pt，防止把页面大标题当成图标名）→ `accessibilityIdentifier`。
  过滤「按钮 / 图片 / 图标 / 更多 / 返回 / 关闭」等空话与纯数字标点。
  来源标注为「名称取自界面控件」，快照性质不变（仍不计为原始文件）。
- `SaoqiangWCAssetsAssociateVisibleIcon` 增加 name 参数：先试 UIKit 私有名称，
  再试传入的名称，最后才退回「无原始资源名」。
- 版本号 0.11.42；CI 卡片断言收紧为「标题顶边距栏底 ≥ 8pt」。

## 四十四、0.11.43：接上微信自己的取图入口 MMThemeManager

- 现象：名称不再是 UUID 了，但绝大多数行还是「无原始资源名」。
- 参考对照：`WeChatUIGrabber 1.8` 的 `WeChatRouteAdapter.h` 只显式挂 5 条路由，
  其中最关键的两条都在**主题管理器**上：
  `-[MMThemeManager imageNamed:]` 与
  `-[MMThemeManager svgImageNamed:size:color:alpha:angle:ignoreNotFound:]`。
  它把名称证据挂在**返回的那个 UIImage 上**，页面采样时直接读，不依赖 CGImage 指针匹配。
- 我们的缺口：此前只挂了 `+[UIImage imageNamed:]` 系列与 WCSVGImage 的动态扫描。
  微信自己的工具栏 / 列表 / 设置页图标根本不走 UIKit 这条路，全是主题管理器发出来的，
  所以这些加载在我们这里全程匿名——采样器无从取名，只能写「无原始资源名」。
- 修复：
  1. 新增 `SaoqiangWCAssetsInstallThemeManagerHooks()`：安装在
     `-[MMThemeManager imageNamed:]`（ABI 校验：3 参数、返回对象）与
     `-[MMThemeManager svgImageNamed:size:color:alpha:angle:ignoreNotFound:]`
     （ABI 校验：8 参数、返回对象、第 3 参 `@`、第 4 参 `CGSize`、第 5 参 `@`）。
     只替换本地方法，签名不符原样放过；类还不可见时下一次调用重试，不做一次性闩锁。
  2. 两条路由都只「观察后转发」：参数即资源名，返回值即后面进 UIImageView / UIButton 的那个对象。
  3. 抓取开关关闭时也把 `CGImage → 名称` 记入备忘表（面板打开前图标就加载完了），
     抓取中则额外走正常的命名/记录流程；即使名称不在记录白名单里，备忘表仍保留，
     保证页面上真的显示出来的图标有可核对的名字。
  4. SVG 结果（渲染成普通 UIImage 的）也补记 CGImage 备忘，图层绘制的 SVG 图标同样能取名。
  5. `SaoqiangWCAssetsRecoveredImageName()` 增加一层 `_cuiImage` 提供者探测，
     与参考实现读取 CoreUI 名称的顺序一致。
- 顺带（用户反馈）：标题不再被挡，但仍然「太上了」。页面容器与导航栏底边的间距
  由 10pt 提到 26pt（标题实际顶到栏底下方 38pt），三个页面统一生效。
- 版本号 0.11.43。
